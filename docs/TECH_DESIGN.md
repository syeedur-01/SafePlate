# TECH_DESIGN.md: how SafePlate works

If a card and this file disagree, **this file wins**. Report the contradiction.

## 1. MVP scope (Oct 23 to Oct 31)

One loop, done well:

**Scan photo → confirm dish → Safety card → Warnings for you → Nutrition card → Swap and shopping list**

- 30 dishes (the closed list in `packages/knowledge/data/source/dishes.json`).
- Two scan kinds: `dish` (photo of a prepared dish plus optional context) and `label` (photo of a packaged-food label). The label path is the first thing cut if time runs out (see `00_INDEX_AND_WORKFLOW.md`).
- Languages: English and Bangla.
- No accounts, no server database, no community feed. The health profile and history live on the device.

## 2. Architecture

```
 Browser (apps/web)                                  Cloudflare Worker (apps/api)
 ┌───────────────────────────────┐                  ┌──────────────────────────┐
 │ UI (React)                    │  POST /api/scan  │ Hono app                 │
 │  - profile (device only)      │ ───────────────► │  validate (strict Zod)   │
 │  - camera/file, downscale     │  image + context │  packages/ai: provider   │
 │ packages/engine (pure TS)     │ ◄─────────────── │   Gemini | Mock          │
 │  - nutrition, safety,         │  dish candidates │  validate model JSON     │
 │    suitability, swaps, list   │  or label fields │  cache + guards          │
 │ packages/knowledge (data)     │  + observations  └──────────────────────────┘
 └───────────────────────────────┘
```

Key decisions:

- The **engine runs in the browser**. The server never sees the health profile, and the Worker's small CPU budget is never spent on rules.
- The API does **one thing**: turn a photo into structured observations, validated against schemas.
- Providers are swappable (`VisionProvider`). Tests and most development use `MockProvider`.
- The API is plain Hono, runnable on Cloudflare Workers (default) and on Node (local dev and the Render fallback).

### Data status on Oct 23 (measured, not assumed)

- 30 dishes, 56 ingredients. Every dish ingredient id exists. No unused ingredients.
- **24 of 56 ingredients have no energy value.** `sat_fat_g` and `sugars_g` are null for all 56. `sodium_mg` is null for 39.
- **No dish can be fully calculated yet** (0 of 30 for energy). Some dishes are mostly missing: for example the share of raw grams with no profile is about 92% for Ilish Bhaja, 68% for Shorshe Ilish, 65% for Dhakaiya Bakarkhani and 53% for Shutki Bhorta.
- 29 dishes have `nutrition_basis: "unavailable"`; 1 (Bangladeshi Chicken Roast) is `lab_analyzed` per 100 g cooked, with `energy_kcal`, `sat_fat_g`, `sugars_g` and `sodium_mg` null.
- Allergen labels use mixed vocabulary (`dairy` and `milk` both appear; also `wheat_gluten`, `tree_nuts`, `crustacean_shellfish`, `mustard`).
- `cooking_method` is free text.

Consequences built into the design:

1. The nutrition engine is **coverage-aware** (section 4.1). It shows a number only when enough of the ingredient mass has data. Otherwise it says "not enough data".
2. Phase 1 data cards try to close the gaps from **permitted sources** (FCTB first, then USDA FoodData Central), as **proposals a human approves**.
3. A **coverage gate** at the end of Phase 2 decides which dishes show numbers in the demo. Dishes below the gate still work for safety, allergens and recognition.

Allowed sources for nutrient values: Food Composition Table for Bangladesh (FCTB 2013), USDA FoodData Central, and INFS (University of Dhaka) cooked-dish studies. Nothing else. USDA matches are **proxy matches** (not Bangladeshi foods) and must be flagged `match_quality: "proxy"`.

## 4. Engine (packages/engine): pure functions

### 4.1 Nutrition

`computeNutrition(dish, ingredientsById, options?) → NutritionResult`

For each nutrient `n` in `NUTRIENT_KEYS`:

1. Ignore ingredient id `water` for both value and coverage (it contributes zero and is not counted in the denominator).
2. `totalGrams` = sum of `grams_raw` of all other ingredient lines.
3. For each line whose ingredient has a non-null `n`: add `grams_raw * value / 100` to `sum`, and `grams_raw` to `coveredGrams`.
4. `coverage = coveredGrams / totalGrams` (0 if `totalGrams` is 0).
5. `value = sum` if `coveredGrams > 0` else `null`.
6. `shown = coverage >= MIN_COVERAGE` (default `0.8`).

If `dish.nutrition_basis === "lab_analyzed"` and `lab_values_per_serving.values[n]` is non-null: use `value = lab * serving_weight_g / 100`, `coverage = 1`, `origin = "lab_scaled"` (still `estimated`, because the serving weight is an estimate). Otherwise `origin = "calculated"` if `coveredGrams > 0`, else `"none"`.

Never derive energy from protein, fat and carbohydrate. Never treat `null` as `0`. `estimated` is always `true` in the MVP.

### 4.2 Safety score

`scoreSafety(input, rules) → SafetyResult`

Input: `{ dish: Dish | null, label: LabelObservation | null, observations: { spoilageSigns, imageQuality }, context, today: string }`.

Rules (`safety-rules.json`) have a `trigger` of one of four types: `spoilage_sign`, `storage_hours`, `dish_tag`, `label_expired`. Each rule has `points` and `labelKey`, `mitigationKeys`, `sourceRef` and `status` (`draft` or `approved`).

`score = min(100, sum of points of triggered rules)`. Levels: `low` if score < 25, `moderate` if < 60, otherwise `high` (constants in one place, `SAFETY_LEVEL_BOUNDS`). Every triggered rule becomes a `signal` with its own evidence text. **No rule triggered means a low score, not a "safe" claim.** `notices` must always contain `notice.chemical_limit` (the honest-limits text below). `rulesStatus` is `draft` if any triggered rule is draft.

The point values are heuristic weights chosen by the team and reviewed by the expert. They are not medical thresholds. The rules' triggers (for example storage hours) must come from verified sources.

### 4.3 Suitability warnings

`evaluateSuitability(profile, dish, nutrition, healthRules) → Warning[]`

- **Allergen conflicts** come first: any overlap between `profile.allergies` and the dish's allergens gives level `avoid` (`kind: "allergen"`).
- **Nutrient rules**: `fraction = nutrition[n].value / dailyLimit`, evaluated only for the user's conditions and only when `nutrition[n].shown`. `fraction >= avoidFraction` gives `avoid`; `fraction >= cautionFraction` gives `caution`. If the nutrient is **not shown**, emit an `info` warning `warn.insufficient_data` naming the nutrient. Never guess.
- **Tag rules**: match on `cooking_class` or `safety_tag` for conditions without a numeric limit.
- Order: allergen `avoid`, then `avoid`, `caution`, `info`.

Wording is always "may not suit you" and "consider limiting", never "will cause". Warnings carry a `sourceRef`.

### 4.4 Other engine functions

- `analyzeLabel(label, profile, rules)`: allergen conflict from declared allergens and keyword scan of ingredients text; expiry check; per-100 g label nutrition against nutrient rules.
- `suggestSwaps(dish, profile, dishes, ingredientsById, healthRules)`: other dishes that improve the user's flagged nutrients with `shown` data, no allergen conflict.
- `buildShoppingList(dish, servings)`: ingredient grams scaled by servings, `water` excluded. No prices in the MVP.
- `analyze(input) → AnalysisResult`: one call that runs everything above. It is the only function the UI calls.

## 5. AI layer (packages/ai)

```ts
interface VisionProvider {
  readonly name: string;
  analyze(req: ScanRequest, ctx: ProviderContext): Promise<unknown>; // raw model JSON, unvalidated
}
```

- `MockProvider`: returns fixtures from `fixtures/mock-scan/`, chosen by a hash of the image or by an explicit header in tests.
- `GeminiProvider`: REST call with the key in a header, `responseMimeType: "application/json"`, image as inline base64. **Model name comes from the `GEMINI_MODEL` env var, never hardcoded.** The REST request shape and the free-tier limits change; the card tells the agent to read the current official docs, and any difference is absorbed inside this one file.
- `runScan(provider, req, ctx)`: call, `parseModelJson`, validate with `ScanResultSchema`, retry **once** on invalid output, then throw `AiInvalidOutputError`.
- `sanitizeDishCandidates`: any candidate id not in the dish list becomes `dishId: null`.
- Prompts list the closed dish list (id, English and Bangla names, aliases) and ask for JSON only. The model never sees the health profile.
- Free tier: assume a small daily request budget. Cache by image hash. Never call the model from tests.

## 6. API (apps/api)

| Method and path   | Request                | Response                        |
| ----------------- | ---------------------- | ------------------------------- |
| `GET /api/health` | none                   | `{ ok: true, version: string }` |
| `POST /api/scan`  | `ScanRequest` (strict) | `ScanResult` or `ApiError`      |

Errors always have the shape `{ error: { code, message } }` with codes `bad_request`, `too_large`, `ai_unavailable`, `ai_invalid_output`, `rate_limited`, `internal`. HTTP statuses: 400, 413, 502, 502, 429, 500.

Env vars: `AI_PROVIDER` (`mock` or `gemini`), `GEMINI_API_KEY`, `GEMINI_MODEL`, `ALLOWED_ORIGIN`. Entries: `src/worker.ts` (Cloudflare), `src/node.ts` (local and Render fallback). Both call `createApp(config)` from `src/app.ts`.

## 7. Web (apps/web)

Screens: Onboarding (language, optional health profile, consent), Scan (camera or file, context chips), Confirm dish (top 3 candidates plus searchable list of all 30), Result (tabs: Safety, For you, Nutrition, Swap and shopping), History, Settings (edit or delete profile, language), About and Sources.

- State: profile in `localStorage` key `sp.profile.v1`; history in `localStorage` key `sp.history.v1` (max 20 entries, thumbnails stored at low resolution only). Delete-my-data clears both.
- Images are downscaled in the browser to a maximum of 1024 px on the long side, JPEG quality 0.8, before upload.
- i18n: `t(key, params)` reads `messages.json`. Missing key shows the key itself and logs a console warning (a test fails on any missing key used by rules).
- Design tokens: Tailwind 3.4 theme; light and dark; risk colours always paired with a word and an icon; minimum tap target 44 px; Bangla font Noto Sans Bengali.
- Always visible on the Result screen: the "estimated" badge on nutrition, the "draft rules" badge when `rulesStatus` is `draft`, and the chemical-limit notice on the Safety card.

## 8. Honest limits (exact text in `messages.json` as `notice.chemical_limit`)

> This check can only look at what a photo and a label show. It cannot detect invisible chemical contamination (for example formalin) or tell you a food is safe. It is general information, not medical or legal advice.

## 9. Free-tier constraints

- Cloudflare Workers free plan: 100,000 requests per day and 10 ms CPU per invocation. Waiting on the AI call does not count as CPU. Keep the Worker thin: no image processing, no heavy parsing. **Spike P1-B04 proves this on day 1; if it fails, switch to Render (Node entry).**
- Gemini free tier: small and changing daily limits, and free-tier content may be used by Google to improve its products. Therefore: no profile data in prompts, cache by hash, mock everywhere in tests.
- No paid services. No database in the MVP.

## 10. Extension points (do not build now, do not block)

- **Accounts:** the web app talks to the API only through `apps/web/src/api/client.ts`. Add auth there later. The profile store has one interface (`ProfileStore`) with a `LocalProfileStore`; a synced store can be added later with opt-in encryption.
- **Community feed:** a separate route group and a separate API module. It must never read the health profile.
- **More dishes and countries:** data-driven. A new country is a new data folder plus rules.

## 11. Vocabulary (single source of truth in `@sp/contracts`)

- Nutrient keys: `energy_kcal, protein_g, fat_g, sat_fat_g, carbs_g, sugars_g, fibre_g, sodium_mg`.
- Conditions: `diabetes, hypertension, high_cholesterol, gastric`.
- Allergens: `milk, egg, fish, crustacean_shellfish, tree_nuts, peanuts, wheat_gluten, soy, sesame, mustard`.
- Safety tags: `dairy, seafood, fried, raw-ingredient, street-food, fermented`.
- Spoilage signs (what the vision model may report): `visible_mold, slimy_surface, discoloration, bloated_packaging, leaking_packaging, separated_liquid, foam_or_bubbles, foreign_object`.
- Cooking classes: `deep_fried, shallow_fried, braised_or_curry, boiled_or_simmered, steamed, baked_or_roasted, mashed_or_raw, fermented, sweet_milk_based, mixed_or_other`.
